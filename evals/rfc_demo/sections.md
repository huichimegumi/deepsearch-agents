# RFC 开发集章节扩展与 Writer 对照

章节扩展沿用原来的混合候选排序和索引。普通问法按第一次命中顺序取最多五个不同章节，从索引读回该章节正文。每节最多 2,200 字符，长章节以命中段落为中心附近截取，并在页面标出截断。明确指定 RFC 和章节的问题继续走原定点路径。

| 普通可回答开发题（7 道） | 原预览 | 章节预览 |
| --- | ---: | ---: |
| 混合候选池包含的标注证据点 | 9/16 | 9/16 |
| 页面实际展示的标注证据点 | 4/16 | 6/16 |
| 展示全部标注出处 | 2/7 | 3/7 |

两次均通过应用入口执行，使用同一索引和混合配置。D04 的 Retry-After 语法与示例现在都在页面出现。D06、D07 的标注证据出现在候选池后段，相关章节未进入五个展示名额。D09 的相关章节仍未进入预览。两道资料不足题仍显示候选原文。此前离线探针的 13/16 衡量的是向量检索选中的完整章节，与此处混合排序下的实际展示口径不同。逐题结果见[原预览](sources.sections-baseline.json)和[章节预览](sources.sections.json)。

## 同证据 Writer 对照

对九道非定点开发题各取一次扩展证据。两种 Writer 接收相同顺序和文本，提示一致，温度为 0，输出上限为 650 token，对照期间各只发一次请求。Qwen3.8 Max 关闭思考模式。Codex 对照冻结参考和引用片段审阅内容。

| 指标 | Qwen Flash | Qwen3.8 Max 0902 |
| --- | ---: | ---: |
| 内容正确，含适当拒答 | 4/9 | 4/9 |
| 部分回答 | 3/9 | 1/9 |
| 内容错误 | 1/9 | 0/9 |
| 可回答题未作答 | 0/9 | 3/9 |
| 引用格式导致交付失败 | 1/9 | 1/9 |
| Writer 耗时中位数 | 1.92 秒 | 2.75 秒 |
| 请求 / 供应商返回 Token | 9 / 22,108 | 9 / 21,890 |

- D01 两组正确，D03 和 D10 两组适当拒答。
- D04 两组答对日期与秒数两种形式及 120 秒，但都遗漏非负整数限制。
- D05 两组都明确禁止 204 响应发送 Content-Length。Max 直接引用 §8.6，Flash 将部分相关陈述挂在 §15.3.5，虽然回答后面也引用了 §8.6。内容通过与逐条引用支持是不同指标。
- D06 缺少目标章节时，Flash 错称所有实体标签都要匹配，Max 拒答。D08 和 D09 也是 Max 拒答，Flash 给出了部分可用内容，但存在漏掉关键条件或引用不能直接支持陈述的情况。
- D07 两组草稿都给出正确的时间比较，所引片段只直接覆盖共享缓存规则，且格式校验失败。单独启用一次重试再试该题，两组均发出两次请求。Flash 第二次仍然格式失败，Max 第二次提示证据不足。重试结果单独保存，未计入九题对照。

本轮保留现有 Writer 配置。Max 处理证据缺口时更常拒答，九题正确数持平，Writer 耗时中位数更高。历史 Flash 的 5/9 来自不同的证据包，不能用它与本次数字直接估计章节扩展的因果效果。所有数字均为开发题结果。[逐题 Writer 指标](writers.sections.json)

## 复现

在 CPU 索引就绪的环境中运行以下命令，每次使用新目录。第三条调用模型，合计最多 18 次请求。

```sh
CUDA_VISIBLE_DEVICES=-1 HF_HUB_OFFLINE=1 uv run python -m evals.rfc_demo.check_sources --baseline NEW_BASELINE_DIR
CUDA_VISIBLE_DEVICES=-1 HF_HUB_OFFLINE=1 uv run python -m evals.rfc_demo.check_sources NEW_SECTION_DIR
CUDA_VISIBLE_DEVICES=-1 HF_HUB_OFFLINE=1 uv run python -m evals.rfc_demo.compare_writers NEW_WRITER_DIR
```

# HTTP 规范查证：页面实际展示的证据

使用 10 道既有开发题和界面共用的 `run_rfc_qa(..., sources_only=True)`。锚点匹配实际渲染的文字，包括截断后的片段；另检查完整候选池，用于区分检索遗漏和展示截断。两次运行均未调用生成模型或读取保留题。未使用重排。

| 类别 | 题数 | 候选池锚点（两次相同） | 原展示 → 按章节优先展示 | 所有标注出处齐全 |
| --- | ---: | ---: | ---: | ---: |
| 普通可回答 | 7 | 9/16 | 3/16 → 4/16 | 1/7 → 2/7 |
| 显式指定章节 | 1 | 3/3 | 2/3 → 2/3 | 0/1 → 0/1 |
| 资料不足 | 2 | 不适用 | 两题仍显示候选片段 | 不适用 |

同一题集、索引和配置下分别运行两次；没有主张两次候选顺序完全一致。修改只让已进入预览候选的不同章节优先各展示一段，仍最多五段。D05 多展示一个标注出处，没有题丢失锚点，因此采用。D04 和 D09 的标注锚点没有进入候选池，本轮不扩展检索；D06、D07 仍有候选中存在而页面未展示的证据。

发布路径的 34 个不同章节链接，均在此前下载的官方 HTML 中找到对应锚点；这不是在线可用性监控。两道资料不足题返回的是候选片段，页面提示打开原文自行核对，没有生成答案，也没有自动判断片段与问题是否相关。不能把片段非空解释为可回答。

耗时中位数分别为 1.02 秒和 0.79 秒，均为一次顺序运行、包含初始化影响，不能据此认定性能提升。11 项问答和查证回归通过。历史保留集及问答成绩不变。

逐题记录：[原展示](sources.baseline.json)、[新展示](sources.diversity.json)。在已有 CPU 索引环境下可用 `uv run python -m evals.rfc_demo.check_sources NEW_DIRECTORY` 复现当前路线；运行目录必须未创建。锚点是有限的证据检查，不能代替人工相关性判断。

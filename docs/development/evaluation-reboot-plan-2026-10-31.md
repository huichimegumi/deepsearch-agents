## 结论

优先做可终止、可评分、可复现的评测闭环，再用对照实验决定模型和研究流程。将 `deepseek-flash` 作为新基线候选，保留 `qwen-flash` 对照。现有证据不能证明模型是主要根因，也不能证明换模型就能解决问题。

建议局部重构运行控制和研究执行路径，保留 Evidence、检索、只读 SQL、确定性费用引擎及产品层。不要以整体换框架为前置工作。第一份完整评分报告必须在 P2 交付，不能一直等到所有失败案例修完。

## 为什么会一直修修补补

1. **执行边界不可靠。** `evals/reports_acceptance/run.py` 使用 `asyncio.wait_for` 包住整个研究过程。它会等待任务实际取消，因此不等于进程硬截止时间；同步 I/O、线程和底层清理都需要进一步定位。历史 1566 秒的确切阻塞点因本机没有原始 Trace，尚未复现确认。
2. **预算和计量没有统一覆盖模型请求边界。** `main_agent.py` 的 agent 循环在模型消息返回后才 `take_llm_call`；客户端还有 `max_retries=1`。目前顶层图事件统计不能直接当作全部子 agent、工具内部模型调用和 HTTP 重试的计费量。应在发送请求前准入、返回后记账。
3. **研究执行逻辑过度集中。** `main_agent.py` 当前 2246 行，混合阶段编排、工具准入、SQL 修复、实体恢复、来源约束、文件交付和异常降级。不同实验开关与默认生产路径并存，单项改善不能自然汇总为完整系统收益。
4. **评测入口和结论分散。** `run_all_evals.py` 仍编排早期 smoke；新的十题入口主要做锁定与汇总，本地和扩展任务分别执行。许多诊断脚本绑定阶段编号、历史 run 和固定案例，适合复盘，不适合持续评测。
5. **缺少自动语义评分的正式出口。** 现有引用检查证明 ID 存在，证据锚点检查证明某段被找到；旧 `run_report_quality_judge.py` 明确不检查事实及证据支持。人工审核未完成时，总体答案指标长期为空。可以先发布明确标注的规则分和模型裁判分，不必将全部进展绑定到人工终审。
6. **开发题持续暴露。** 旧十题和已运行过的 RAG test 都应保留为回归资产；不能通过不断修复同一批题后宣称独立泛化提升。部分目录/专栏修复有价值，但不能代替新文档上的测试。

这几项是工程与实验设计问题。qwen-flash 的工具选择、跨源推理、证据忠实度也可能影响成绩，需要控制变量验证。

## 目标协议

“评测跑完”定义为：每个排定题目都有终态、原始输出或明确失败记录、评分结果或解释清楚的不可评分原因，最终自动生成汇总。它不要求所有题回答正确。

每轮至少交付：

- `manifest.json`：源码/依赖锁/语料/数据集/评分器哈希、模型请求名及响应名、thinking 配置、预算、索引版本。
- `cases/<id>/<attempt>/`：任务输入、工具事件、Evidence、候选与实际交付答案、终态、评分。逐步写盘，崩溃后仍保留已完成步骤。
- `results.jsonl`：逐题一条规范结果，失败不丢失；历史 attempt 不覆盖。
- `summary.json` 与 `report.md`：全体分母、分类成绩、延时、资源使用、主要错误及配置对照。

运行入口与评分入口分离，后续 CLI 形状建议为：

```text
python -m evals.cli preflight --suite regression_v3
python -m evals.cli run --suite regression_v3 --profile deepseek_baseline
python -m evals.cli score --run <run_id> --judge <frozen_judge_profile>
python -m evals.cli compare --runs <baseline_id> <candidate_id>
python -m evals.cli resume --run <run_id>
```

以上是待实现的接口，不是当前可直接执行的命令。

## 分阶段实施

### P0：恢复评测资产并冻结协议

工作：

- 使用已冻结的公开 DABStep、Adyen dev 与 HybridDeepResearch release 资产，校验哈希并构建 SQLite。旧 PDF 不在当前服务器，新的 v3 不依赖它们；历史记录继续保留。
- 从现有十题建立开发回归集；旧语料缺失时明确标记哪些题暂不能复现，并以新公开语料建立首轮可执行小集，不伪造与旧分数的连续性。
- 固定题目、答案要点、数值/单位、支持原文、可回答性、允许来源、预算和评分规则。先区分“未找到”“工具失败”“语料中没有答案”。
- 对原题歧义和标注缺口在运行前定稿；执行后发现歧义则公开标记并建立下版，不能为了提高本轮分数临时换答案。
- 为自然路由评测禁止传入隐藏 `expected_route`；用户题目明确给出的来源要求可以传入。SQL gold、答案标签只给 scorer。

交付与验收：可重新构建索引/数据库的资产清单、冻结 suite、一次无模型的 preflight。缺失资产在执行前报出，不能消耗模型或搜索额度后才发现。

建议提交：`feat(evals): freeze reproducible evaluation assets and scoring protocol`。

### P1：统一执行器和硬超时

工作：

- 每题独立 worker 进程，父进程维护 deadline。正常超时先取消，给予短清理时间，仍未退出则终止进程树；Linux 与 Windows 都验证。父进程负责写 timeout 终态并继续下一题。
- 模型与工具共享单调时钟 deadline；请求 timeout 小于剩余预算。SDK 隐式重试关闭或纳入统一重试策略，只重试明确的暂时性错误，最多一次，取消后不得再开新调用。
- 请求前统一扣减额度，所有角色、子 agent 和重试分别记录。逻辑调用、HTTP attempt、tokens、查询数、页面数和 provider credits 各自计量。
- Trace/Evidence 增量落盘；恢复只重跑未结束题目。预算在父进程持久化，防止 worker 重启使全局额度归零。
- 首轮并发 1，隔离会话、checkpoint、环境配置和模型缓存；批次评测默认关闭长期记忆读写。
- 合并现有 runner 的执行路径，保留旧模块作为适配器。

验收：故障注入覆盖永久等待、慢清理、同步阻塞、429/5xx、异常进程退出；一题失败不阻塞其他题。默认 300 秒业务预算、330 秒外层 deadline、5 秒清理窗口；在受支持测试环境内最迟 335 秒记录终态并继续。外部服务端是否已停止计费不能由本地 kill 保证，应记录在途请求。

建议提交：`fix(runtime): bound evaluation workers and persist terminal results`。

### P2：跑出第一份完整评分基线

工作：

- 统一规则 scorer 与 evidence-aware judge；将目前多个审阅工具的通用原文绑定校验复用进 scorer，而不是再加一个阶段专用审阅脚本。
- 实现简单参考流程：实际检索/执行 SQL → 一次结构化回答 → 后端引用渲染。使用同一套真实工具和输入预算，不喂 gold Evidence；另设 gold Evidence 诊断模式，绝不计入端到端成绩。
- 用 DeepSeek 在可复现十题上运行旧流程及简单参考流程，并自动完成评分。若只能先构建较小新集，明确报告其数量和范围，不继续等待旧资产。
- 裁判独立配置，固定模型、prompt、rubric 和版本；优先与生成器不同模型，避免同模型自评成为唯一证据。无合适独立裁判时，先发布客观子分和明确标注的模型暂评，不宣称人工准确率。
- 用有确定支持/矛盾/漏答标签的校准案例验证评分器；审查分歧及抽样报告。人工审核可以提高可信度，但不阻塞自动报告生成。

验收：全部排定题有结果；有可见的答案要点分、引用支持分和失败分类。即便结果较低，也发布基线。不能只交付“机械通过、人工待审”。

建议提交：`feat(evals): score grounded answers and publish the first complete baseline`。

### P3：区分模型问题与流程问题

先冻结 6 个有代表性的开发案例：3 个本地题（含多文档与无答案）、1 个 SQL、1 个 SQL＋本地、1 个 Web。新增加的 SQL 题使用确定性参考结果。

做两种不同实验：

1. **固定证据实验**：同一 Evidence 输入给两个模型，比较要点覆盖、数值正确性、拒答和引用支持。仅诊断阅读/选证/写作，不称为检索或端到端评测。
2. **完整流程 2×2 对照**：旧流程/简单流程 × qwen-flash/deepseek-flash，共 24 个题目运行。检索配置、来源限制、deadline 和最大资源预算相同；不按模型偷偷扩大限额。模型的实际使用量单独报告。

缓存按完整工具请求、参数、语料/网页快照版本寻址，不能按题号把好证据强塞给不同查询。完整流程遇到新查询时允许按冻结额度真实执行，或明确记录 cache miss；强制同一证据输入只属于第一类诊断。

从校准后的 judge 和逐题结果判断：固定证据下差距大，优先换模型/改选证写作；固定证据好、完整流程差，优先研究调度；两模型都缺同一证据，优先检索；语义无差但延时变化大，优先客户端/服务质量。6 题只作开发判断，对关键差异做少量配对重复，不能据一次运行宣称模型普遍优劣。

首轮 DeepSeek 保持当前 non-thinking 配置；thinking 作为单独实验，确认多轮工具协议后再启用。API 名称可能指向更新后的模型，因此记录测试日期与响应标识。

建议提交：`feat(evals): add paired model and workflow comparisons`。

### P4：按证据做局部重构，最多一轮重点改进

目标执行链：任务约束/问题拆分 → 有界取证 → 证据存储 → 一次缺口检查与可选补查 → 结构化回答 → 引用渲染及交付验证。

- 本地、SQL、Web 以 source adapter 共享 EvidenceRecord；简单本地题直接检索。混合来源由显式依赖图调度，例如 SQL 的实体值进入 Web 查询；不依赖 supervisor 无限制反复委派。
- 复杂自适应研究保留可选 agent 路径，由对照结果决定何时使用，不将所有请求强行走同一条重链路。
- 保留现有稳定 Evidence ID，模型选择已有短引用键/原文片段，后端映射并渲染引用。引用身份校验与语义支持校验继续分开。
- 小上下文允许取证后直接 Writer；长上下文才选证压缩。压缩只交付原文片段、定位与未解决问题，减少多次自由改写造成的信息损失。
- 允许一次有明确缺口的补查；预算耗尽输出实际证据范围内的部分回答或拒答。原候选与实际交付分开保存，方便判断保护措施是否改善可信度、是否降低覆盖。
- 将执行入口、预算、模型配置、来源适配、回答渲染拆成职责清楚的模块。保留 API、UI、登录、会话和存储，继续复用原来的只读 SQL、检索与费用引擎。
- 提示词/检索/模型每轮只改一类变量；默认流程升级需要跨案例改善，不能凭一个目录题通过。

验收：同版十题复验，比较正确性、引用支持、无答案处理和资源使用；不靠放宽 grader 获取提升。目标可设为至少 9/10 无运行异常、所有交付引用 ID 合法，质量提升与简单基线逐题对比；达不到也记录结果，停止本轮继续修同一题，进入独立验证。

建议提交：`refactor(research): execute bounded evidence workflows with structured answers`。

### P5：独立小集验证并交付结论

- 冻结 20 个新题：8 本地（含 2 个无答案）、4 SQL、4 Web、4 混合来源。尽量使用新文档/新表，包含自然问法、结构问法、数值、多文档和来源冲突。
- 由资料原文和独立参考计算建立标签；生成器不可见。当前开发过程中已经阅读/讨论过的题只能进入 dev。人工作者不可用时，可从已发布任务按规则抽样或用独立配置生成候选并校验，但要披露其独立性限制。
- 固定最终实现与简单基线，用同一模型和预算比较。第一轮独立测试结束即出报告；若根据错误调优，该集合从此转为开发回归，下一次需要新 holdout。
- 后续可加 5 个分层抽样的 DeepResearch Bench 题，导出官方格式；现有 Hybrid 三题继续做跨源 smoke。官方 scorer、judge 或抓取依赖未准备好时单独记录，不阻塞内部评测交付。
- 新旧版本产生一个完整报告，含低分、失败和局限，不再以新增单元测试数作为评测成果。

建议提交：`feat(evals): publish held-out evaluation and reproducibility report`。

## 指标和分母

| 指标 | 口径 |
| --- | --- |
| 批次终态覆盖率 | 有终态的题数 / 排定题数；目标 100%，timeout 也必须留记录 |
| 运行完成率 | 无运行错误且完成执行的题数 / 通过预检并启动的题数；同时公布预检阻塞数 |
| 端到端任务通过率 | 满足预先冻结的任务要点、来源与事实要求的题数 / 全部有效排定题；空答和 timeout 不从分母删除 |
| 问题要点覆盖 | 对每个要点评正确、部分、遗漏/错误，逐题先平均再汇总；同时展示原始计数 |
| SQL 正确性 | agent 生成并执行的查询结果与独立参考结果比较；显式处理排序、重复、NULL、单位与数值容差 |
| 引用合法性 | 引用是否能解析到当前题实际取证记录；这是机械指标 |
| 引用支持率 | 被引用原文支持的事实陈述 / 可评的引用事实陈述；另报缺引事实比例，避免少写少引得高分 |
| 无答案处理 | 在无答案题上正确限定证据范围/拒答；在可回答题上单列错误拒答率 |
| 检索诊断 | evidence Recall@k、MRR、必需来源覆盖；不替代答案成绩 |
| 资源 | p50/p95、实际请求与重试、tokens、搜索查询/抓取/credits、每个成功任务成本；小样本同时给逐题耗时 |

运行状态、交付状态、内容评分分别保存。degraded 报告也评内容，避免只审成功题造成幸存者偏差；主端到端通过率仍按冻结的完整要求判断。裁判失败标成 `judge_error` 并显示评分覆盖率，可离线重试评分，不能重跑研究来覆盖失败。

数据缺失或坏题必须在运行前处理；测试中才发现的问题保留在原分母与附加敏感性分析中，不能静默排除。人工未审核时可以发布规则成绩与 LLM judge 成绩，但名称明确，不冒称人工准确率。

## 预算、停止条件与提交方式

- 当前调研只用了 3 次 DeepSeek 小请求、0 次 Tavily 搜索。后续付费额度为计划值。
- 首轮 P0–P4 建议全局 Tavily 上限 20 次实际查询请求，P5 内部独立验证上限 30 次；合计 50 次。credits 另行记录，查询次数不等于 credits。提前预留请求重试额度，禁止 auto 后端暗中切入其他付费服务。
- 模型对照优先本地/SQL和固定证据诊断，网页正文与搜索响应缓存。新查询不能伪造命中；超出预算保留 budget_exhausted 结果，不换更容易的题。
- 额外 5 题公开 benchmark 独立列预算，例如最多 15 次搜索请求，并记录是否因预算受限。小预算成绩不与大预算全量榜单直接比较。
- LLM 在 P0 冻结 input/output token 预算和货币上限，worker 启动前预留最坏输出额度；不能只限制逻辑调用次数而忽略长上下文、重试及评审成本。
- P2 必须交第一份完整基线。P4 限一次主要修复及一次同条件复验；结果不好也进入 P5 出结论。之后按新评测报告立项，禁止单题不断衍生几十个阶段。
- 每阶段独立 commit，正文写清问题、设计、验证、真实结果、资源使用和未解决事项；只有完成当阶段验收才推进。未来实施时按用户当次授权 push。本次只新增计划文档。

## 技术依据

- [Python 3.12 asyncio.wait_for](https://docs.python.org/3.12/library/asyncio-task.html#asyncio.wait_for)：会等待取消实际完成，等待可超过 timeout；这解释了为什么当前外层包装不足以保证硬截止，但不构成对历史阻塞点的完整诊断。
- [DeepSeek API 接入](https://api-docs.deepseek.com/en/)：当前公开 API 支持 `deepseek-flash`。本次实际请求也返回该模型名；别名背后的版本应在评测日期记录。
- [DeepSeek thinking 配置](https://api-docs.deepseek.com/guides/thinking_mode/)：thinking 与工具多轮协议需要显式适配；当前项目 smoke 使用 non-thinking，不代表已验证 thinking 工作流。

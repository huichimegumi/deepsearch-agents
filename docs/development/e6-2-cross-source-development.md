# E6-2：跨来源开发与一次集中修复

新增内部工程集，公开来源为 RFC Editor 的未修改 RFC 文本和 JSON 元数据。它不是官方榜单 benchmark。22 份 RFC 分为文档级不重叠的开发来源 10 份、验证来源 12 份；文本和元数据共 44 个文件的 URL、字节数、SHA256 位于 `evals/standards/sources.lock.json`。原文只下载到忽略的数据目录，保留其版权声明。源自 RFC 4627/8259 的 JSON 版本差异、RFC 2396/3986 的 URI 分类差异用于开发冲突题。Web 评分使用完整锁定正文上的查询检索，不把快照当实时搜索成绩。

开发 16 题：SQL、文档、Web、SQL→Web 各 4 题，文档含 2 道限定证据的无答案题。数据库从出版社元数据导入，数值参考通过独立 Python reduction 得到，而非调用生成器查询。应用先看真实 schema，自行写 SQL；所有同分区题共享完整文档集合，由问题驱动检索，不按题号灌入好片段。公开任务投影只有问题、来源限制、ID；oracle/checklist 仅父进程评分器读取。混合题还机械核对实际执行过的 SQL→Web 依赖，而不只统计两种来源是否出现。

新增独立 worker 执行器 `evals.run_v4`：CPU、每题 210 秒外部硬超时、应用内 180 秒、最多 8 次请求和 180k 估算预留 token，批次 2M；逐题保存结果，已终态不重跑。源码或数据变化拒绝续跑，并在执行每题前复查源码。v4.1 相对 v4.0 新增混合依赖核对；原评分版本与原始结果保留。

诊断确认 Writer 会把“not specified”等定性结论放入数值字段；另有模型自选步骤编号与模板编号不一致。集中修复为明确数值/定性 schema 边界、无结构化数字时 facts=[]、由后端按数组位置生成步骤 ID、SQL→Web 强制采用真实依赖模板。解析失败候选保存在 rejected_candidate.json，已返回的失败请求也尽量保留 usage。没有放宽评分规则。

仍有两题因 Gap.reason 超过 400 字符而降级，正常完成率 87.5%，**未达到 90% 目标**。另有拒答标签与正确的限制说明不一致、混合答案引用支持不足的问题。两道开发无答案题的“无通用数字”与“完整解释不存在通用数字”之间存在标签解释边界，结果保留在原分母，不通过改标签提高成绩。按计划停止继续修改同一集合，冻结实现进入新来源的 24 题验证。当前不提升新流程为默认。

复现：`python -m evals.standards.prepare` 校验下载和重建数据库；`python -m evals.run_v4 --split dev --workflow bounded --output <新目录> --score`。初次 run `e6-2-dev-bounded`；修复 run `e6-2-dev-repaired`。报告见 `evals/reports/e6-2-dev-*.md/json`。评分是单次 DeepSeek claim/checklist 判断，受 E6-0 校准约束但仍为暂定；SQL 数值与引用身份独立机械验证。实际成本用请求、预留及已返回 token 报告，不把估算预留当作供应商计费。

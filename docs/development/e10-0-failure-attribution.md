# E10-0：从现有失败记录确定修复范围

E9 的门槛失败保持不变。此阶段只读取八道已暴露开发题的记录，不请求模型，不下载新题，不占用 GPU。可复现入口：`python -m evals.diagnostics.attribute_e10 --output evals/reports/e10-0-attribution.json`。

SQL 六题按最终实际状态分为：两题空结果不匹配，一题非空结果不匹配，一题 SQL 执行错误，一题结构化输出错误，一题 API 超时。后两项没有有效 SQL，不纳入“语义错误已确认”的分母。参考 SQL 在此前控制中可重现参考结果，但其字面量提示没有字段和匹配方式标签，不能假设真实上游已经正确。

两道空结果题均把包含通配符的绑定值用于等号，而参考查询使用 LIKE；两次候选完全相同。它们还存在派生指标、筛选或聚合表达式不同。非空不匹配题也更换了指标公式和条件。执行错误题重复生成相同候选，含不支持的语法。这些发现要求修复可执行语义与实际错误反馈，不能只检查访问过哪些字段。

另一个明确的输入缺口是：六题选中的五条知识定义均缺少直接依赖，缺少数量依次为 1、1、1、2、2、3。`describe` 目前按词项相关度选前五条，没有补依赖。不能要求模型忠实使用没有提供的公式；下一阶段先补齐有预算限制的定义依赖，再实现有限的结构化查询编译。依赖缺失是输入事实，不单独证明每题失败的原因。

报告三题失败分为：引用不完整结果表；SectionText 多生成不允许的 section 字段/无可解析候选；若干单条 claim 的 refs 超过上限。后端原始行没有丢失。下一阶段由后端确定章节/表格，减少模型负责的输出结构，逐条隔离错误；不把超长引用静默截断，不把预览提升成完整结果。

公开归因 JSON 只包含案例 ID、计数、类别和摘要哈希。词法特征只是复核信号，不是 SQL 等价判定；完整问题、参考 SQL、标识符、业务常量、失败候选继续留在忽略目录。

阶段顺序：E10-1 有限查询编译与知识依赖；E10-2 报告职责及错误隔离；E10-3 预先固定的小规模 Qwen canary。组件门槛仍为报告 8/8、辅助 SQL 至少 4/6；不满足就停止，不进入完整开发和独立验证。canary 不能冒充整组组件或端到端成绩。每阶段分别验证、commit、push，不新增付费搜索或 DeepSeek 调用。

验证：归因测试 2 passed，Ruff 检查通过；归因脚本对实际存档成功完成，零 API 调用。

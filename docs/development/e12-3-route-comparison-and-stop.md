## 列名错误暴露的后端问题

四次基线执行报错的列名实际上都已出现在公开 catalog 中。后端只创建 cN/mN 列，而上下文同时展示原字段名，形成了接口不一致。因此不能把基线失败直接归为 Qwen 不会写 SQL。

随后只做离线修复：内存关系增加公开原字段/指标名称的精确且无歧义别名，别名和短 ID 指向同一个原始单元格；不修改候选 SQL 的筛选、排序、条数、公式或字段选择，不猜测新字段。仍不能访问原数据库、写入或调用未批准函数。新上下文明确标出 sql_alias。

## 不调用模型的保存输出回放

复现入口：`python -m evals.diagnostics.compare_e12 --output evals/results/e12-comparison --offline-replay NEW_DIR`。只允许后端源码版本变化，原输入、协议、数据库和参考哈希仍须一致。每份保存 SQL 必须与原始模型 trace 的 parsed 参数相同，否则拒绝。各次尝试全部记录，以最后一次为主，不挑最好输出；此入口不创建模型。

修复后的四份保存 SQL 都能执行，但按原比较器，最后尝试仍为 **0/2**。其中一题返回的原始名称文本与参考查询选中的原始名称一致，却有额外列和名称格式差异；另一题原始名称也不一致。原始名称诊断仅在评分侧移除参考查询的名称格式投影，保留过滤与排序，不用于生成、不替代严格 SQL 等价检查，也不能证明实体唯一性或整条查询正确。

原始线上 0/2 与离线回放分别保留，没有把后端修复后的回放冒充新模型成绩，没有放松比较器来通过门槛。公开摘要为 evals/reports/e12-3-route-comparison.json。完整问题、SQL、候选值、查询结果和 trace 留在忽略目录。
